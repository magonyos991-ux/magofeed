# Magofeed
#
# A LIRE AVANT DE COMPTER DESSUS : sur une adresse GitHub Pages de projet
# (magonyos991-ux.github.io/magofeed/), ce fichier n'est PAS lu par Google.
# Les moteurs ne lisent le robots.txt qu'a la racine du domaine, c'est-a-dire
# magonyos991-ux.github.io/robots.txt — une adresse qui ne nous appartient pas
# et qui renvoie 404 (verifie). Ce fichier ne devient reellement actif que le
# jour d'un nom de domaine a nous (magofeed.be par exemple). Il est ecrit
# d'avance pour ce jour-la.
#
# POURQUOI IL N'Y A PLUS DE « Disallow: /f/ » ICI.
# Les pages de /f/ ne doivent pas etre indexees, et elles ne le sont pas :
# chacune porte <meta name="robots" content="noindex,follow">, une balise lue
# partout et qui marche des aujourd'hui. La ligne « Disallow: /f/ » semblait
# renforcer cette protection. Elle l'aurait DETRUITE.
#
# Google est explicite la-dessus :
#   « For the noindex rule to be effective, the page must not be blocked by a
#     robots.txt file. If the page is blocked by a robots.txt file, the crawler
#     will never see the noindex rule, and the page can still appear in search
#     results. »
#   https://developers.google.com/search/docs/crawling-indexing/block-indexing
#
# Autrement dit : interdire le passage empeche le robot de LIRE la consigne de
# ne pas indexer. Les 570 pages pouvaient alors ressortir dans les resultats,
# sans titre ni description, faute d'avoir pu etre lues. Le piege etait
# inoffensif tant que ce fichier n'est lu par personne — il se serait arme tout
# seul le jour du nom de domaine. On le retire pendant qu'il ne coute rien.
#
# La regle est donc : on LAISSE passer le robot sur /f/, et c'est la balise
# noindex de chaque page qui fait le travail. Les robots des reseaux sociaux
# ignorent cette balise : les apercus de liens partages continuent de
# s'afficher normalement.
